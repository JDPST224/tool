# project_down — HTTP load / stress tester

A small Go load tester for HTTP/1.1 and HTTP/2 servers. It supports direct
connections, HTTP/HTTPS proxies, SOCKS4 and SOCKS5, custom `Host`/TLS `SNI`,
optional per-request jitter, and live throughput/error reporting. Requests use a
coherent browser-like session by default: stable UA/Client Hints/language/cookies
per connection, browser-style header order, matching `Sec-Fetch`/`Referer`/
`Origin` headers, a matching browser TLS ClientHello (uTLS), and a matching
HTTP/2 connection preface. Proxies, browser identities, and fingerprints rotate
per connection. By default it sends requests without waiting for responses;
response-aware status/latency mode is available with `--send-only=false`.

Use it only against servers you own or have explicit permission to test.
Running this against third-party systems is abuse and may be illegal.

## Requirements

- Go 1.25+ to build from source (the included `tool.exe` is a Windows
  build and does not need Go installed).
- `golang.org/x/net` and `github.com/refraction-networking/utls` (installed
  automatically by `go mod download`). uTLS provides the browser TLS
  ClientHello profiles; HTTP/2 framing uses `golang.org/x/net/http2`.

## Build

```powershell
go build -o tool.exe .
```

On Linux/macOS:

```bash
go build -o tool .
```

Run the tests with:

```bash
go test ./...
```

Run the request-generation benchmarks with:

```bash
go test -run '^$' -bench . -benchmem
```

## Usage

```text
tool.exe [flags] <URL> <THREADS> <DURATION_SEC> [CUSTOM_HOST]              (direct)
tool.exe [flags] <URL> <THREADS> <DURATION_SEC> <PROXY_TYPE> [CUSTOM_HOST]  (proxy)
```

The positional arguments are unchanged; all new behavior is controlled by
optional flags placed before them. By default, requests are sent without waiting
for or parsing responses. No mode flag is required.

- `PROXY_TYPE`: `http`, `https`, `sock4`, or `sock5`
- `CUSTOM_HOST`: value used for the `Host` header and TLS SNI. It may include a
  port. If it has no port, a non-default target port is appended automatically.
  Because the CLI has no explicit mode flag, a custom-host value equal to a
  proxy type name (`http`, `https`, `sock4`, `sock5`) selects proxy mode; add an
  explicit port in that unusual case.
- `--jitter <ms>`: random sleep of 1..N ms between requests. Optional,
  default `0`. Put flags **before** the positional arguments.
- `--send-only`: send-only mode, **default `true`**. A background reader
  discards response bytes to prevent TCP receive-buffer backpressure from
  stalling the writer. Statistics count requests written, not completed
  responses.
- `--send-only=false`: response-aware mode. Waits for each complete response,
  drains its body, and reports status codes and latency.
- `--cache-bust`: append a random query parameter to GET/HEAD requests. Off by
  default because real browser requests use the URL exactly as given.
- `--xff`: add a synthetic `X-Forwarded-For` chain. Off by default because real
  browsers do not send that header; useful for CDN/proxy-chain testing.
- `--fingerprint <mode>`: browser TLS/HTTP2 profile. `rotate` (**default**)
  picks a new coherent browser identity for each connection; `chrome`,
  `firefox`, `safari`, and `ios` pin the family; `none` disables mimicry and
  forces HTTP/1.1 with Go's TLS stack.
- `--http2`: negotiate HTTP/2 over TLS when the server supports it
  (**default `true`**). Servers that do not negotiate `h2` use HTTP/1.1.
- `--proxy-rotation <mode>`: how a new connection chooses a proxy:
  `round-robin` (**default**), `random`, or `sticky`.
- `--rotate-every <n>`: reconnect after `n` requests on a connection, which
  also rotates the proxy and browser fingerprint. Default `0` (only rotate when
  the connection ends naturally). Useful when testing long-lived keep-alive
  connections.

Browser-like request profile:

- One coherent browser identity per connection: stable User-Agent, Client Hints,
  Accept-Language, and analytics-cookie set across the requests on that
  connection. A new connection gets a new identity when rotation is enabled.
- Mostly GET navigations, with occasional form POSTs and fetch-style HEADs.
- Coherent `Sec-Fetch-Site` / `Referer` combinations: direct navigation has no
  Referer and `Sec-Fetch-Site: none`; external referers are cross-site;
  form POSTs and fetch HEADs are same-origin.
- Chrome requests use matching `sec-ch-ua`, mobile/platform hints, and
  `Priority` when appropriate.
- Header order follows a Chrome-like pattern.
- No synthetic `X-Forwarded-For` or forced `Cache-Control`/`Pragma` headers by
  default. Random query parameters are off unless `--cache-bust` is used.

### TLS and HTTP/2 fingerprint mimicry

The TLS ClientHello is generated by
[`uTLS`](https://github.com/refraction-networking/utls), and the HTTP/2
connection preface is written directly rather than by Go's `net/http`
transport. The profile follows the session's browser family:

| Profile | TLS ClientHello | HTTP/2 SETTINGS / WINDOW_UPDATE | Pseudo-header order |
| --- | --- | --- | --- |
| Chrome | Chrome 120 / 131 / 133 | `1:65536;2:0;4:6291456;6:262144`, WU 15663105, no PRIORITY frames | `m,a,s,p` |
| Firefox | Firefox 102 / 105 / 120 | `1:65536;4:131072;5:16384`, WU 12517377, Firefox priority tree | `m,p,a,s` |
| Safari | Safari 16 | `2:0;3:100;4:2097152;8:1;9:1`, WU 10420225 | `m,s,a,p` |
| iOS Safari | iOS 12.1 / 13 / 14 | Safari/CFNetwork settings | `m,s,a,p` |

HTTP/2 is negotiated with ALPN (`h2`, then `http/1.1`). If the server selects
HTTP/1.1, the tool falls back to its raw HTTP/1.1 request path. HTTP/2 is only
used for HTTPS targets, matching browser behavior; plain `http://` targets use
HTTP/1.1. A server that does not negotiate `h2` is not forced into HTTP/2.

Fingerprints are rotated per connection. Use `--rotate-every` to recycle a
long-lived connection and force a new proxy/fingerprint, or pin one family with
`--fingerprint=chrome`, `firefox`, `safari`, or `ios`. `--fingerprint=none`
uses Go's regular TLS stack, advertises only `http/1.1`, and is intended for
baseline comparisons.

This does not execute JavaScript or fetch page subresources, so it mimics
browser network fingerprints and request headers rather than a full browser
session. TLS certificates are still not verified, so self-signed home-lab
certificates work.

Examples:

```powershell
# Direct send-only (default): 50 connections for 30 seconds
.\tool.exe http://192.168.1.20:8080/ 50 30

# Direct HTTPS, send example.com as Host/SNI while connecting to the URL host
.\tool.exe https://203.0.113.10/ 50 30 example.com

# Proxy mode: 100 connections, 60 seconds, HTTP proxies from proxies.txt
.\tool.exe https://example.com/ 100 60 http

# Proxy mode with a custom Host/SNI value
.\tool.exe https://203.0.113.10/ 100 60 http example.com

# Proxy mode with a 10 ms maximum jitter
.\tool.exe --jitter 10 http://example.com/ 100 60 socks5

# Response-aware mode: wait for responses and report status codes/latency
.\tool.exe --send-only=false https://example.com/ 20 30

# Force a Chrome TLS/HTTP2 fingerprint and start 25 connections
.\tool.exe --fingerprint=chrome https://example.com/ 25 30

# Rotate proxy and fingerprint every 500 requests on a long-lived connection
.\tool.exe --rotate-every 500 https://example.com/ 100 60 http

# Random proxy selection instead of round-robin
.\tool.exe --proxy-rotation=random https://example.com/ 100 60 socks5

# Force HTTP/1.1 (no h2 ALPN) while keeping the browser TLS fingerprint
.\tool.exe --http2=false https://example.com/ 20 30

# Optional CDN/proxy-chain testing (non-browser-like)
.\tool.exe --cache-bust --xff https://example.com/ 50 30
```

### proxies.txt

`proxies.txt` is read when a proxy type is supplied. One proxy per line:

```text
# comments and blank lines are ignored
127.0.0.1:8080
10.0.0.5:3128
[::1]:1080
http://192.0.2.10:3128
```

The scheme prefix is optional and only informative: the `PROXY_TYPE` argument
decides the protocol. Proxy authentication is not supported. Invalid lines are
reported with their line number. See `proxies.example.txt`.

Each new connection selects a proxy according to `--proxy-rotation`:

- `round-robin` (default): successive connections cycle through the list.
- `random`: each connection picks a random entry.
- `sticky`: a worker keeps its assigned proxy until that proxy fails.

A proxy that fails to connect or fails before completing any request is skipped
for a 15-second cooldown, then becomes eligible again. With `--rotate-every`,
connections are recycled on a fixed request count so proxy and fingerprint
rotation also happen against keep-alive servers.

## What the output means

By default, each thread writes requests back-to-back and does not wait for,
parse, or classify responses. A background reader discards response bytes so
that unread data does not fill the TCP receive buffer and block the writer. This
gives maximum send pressure, but status codes and response latency are not
available in this mode.

Send-only mode batches up to 64 requests (or 64 KiB) per socket write on
HTTP/1.1, uses a 32 KiB discard-read buffer, and reuses per-connection buffers.
`--jitter` keeps one request per write so jitter spacing is preserved. On
HTTP/2, send-only mode keeps up to 64 streams in flight per connection and
drains response frames to keep flow-control windows open.

With `--send-only=false`, every thread keeps one connection open and waits for
each complete response (headers **and** body) before sending the next request.
HTTP/2 uses one stream at a time per worker in this mode. This makes the numbers
reflect work the server actually completed instead of bytes that only reached
the client's socket buffer.

Default (send-only) statistics:

- `req/s`: successfully written requests per second during the last interval.
- `sent`: requests written during the last interval.
- `total_sent`: requests written during the whole run.
- `errors`: transport errors, including write timeouts and connections closed
  by the server.
- `timeouts`: subset of `errors` caused by a timeout.

Response-aware (`--send-only=false`) statistics:

- `req/s`: completed responses per second during the last interval.
- `responses`: completed HTTP exchanges.
- `errors`: transport errors (connect failures, resets, read/write errors).
- `timeouts`: subset of `errors` caused by a timeout.
- `2xx` / `3xx` / `4xx` / `5xx`: completed responses by status class. A `5xx`
  is not counted as a transport error; it is reported separately.
- `avg_ms`: average time from sending a request through receiving the full
  response body.
- `other`: unusual status codes (600+).

The final line (`stress test completed`) contains totals, overall throughput,
and either send-only request totals or response/status totals.

## Testing a home server before moving to a VPS

1. Run the tester from a **different machine** than the server. Testing over
   loopback measures the client and server on the same CPU, not network/stack
   capacity.
2. Start small: `10–25` threads for a `20–30` second run. Watch server CPU, RAM,
   disk, network, and application logs.
3. Increase threads gradually (for example 25 → 50 → 100) and repeat the same
   duration. Use `--send-only=false` first to verify status codes and latency,
   then use the default send-only mode for maximum outbound request pressure.
4. Keep the target endpoint and request mix consistent between the home and VPS
   runs. Requests are mostly GET navigations with occasional form POSTs and
   fetch HEADs, so use an endpoint where the occasional POST is harmless (or a
   test path that accepts them).
5. Test both protocol paths if your server supports them: run once with the
   default `--http2=true` and once with `--http2=false`. HTTP/2 multiplexes many
   requests per connection, so its concurrency/CPU profile differs from
   HTTP/1.1. Use `--fingerprint=none` as a baseline if you want to separate
   server capacity from fingerprint-mimicry overhead.
6. When you move to the VPS, run the same command from the same client network.
   Your home upload bandwidth (or Wi-Fi) can be the bottleneck, not the VPS.
7. A useful capacity result is the highest thread count where the server keeps
   returning successful responses with acceptable latency and no errors — not
   the highest momentary `req/s`.

## Notes and limitations

- HTTP/1.1 and HTTP/2 over TLS are supported. Redirects and `Set-Cookie` are
  not followed/processed; `3xx` responses are counted in response-aware mode.
- HTTP/2 is used only for HTTPS targets (browsers do not use h2c). If ALPN does
  not select `h2`, the tool uses HTTP/1.1. HTTP/3 is not supported.
- The browser-like profile mimics request headers, TLS ClientHello structure,
  and HTTP/2 startup frames. It does not execute JavaScript, fetch page
  subresources, follow redirects, or run a real browser session. TLS
  profiles are matched to the UA family and version where uTLS provides a
  profile; Safari/iOS HTTP/2 settings are representative of current CFNetwork
  rather than version-exact. Cookies are synthetic and stable per connection,
  not a real cookie jar.
- Fingerprint rotation happens per connection because a TLS ClientHello and
  HTTP/2 SETTINGS frame can only be sent once per connection. Use
  `--rotate-every` to recycle long-lived connections.
- Direct mode resolves IPv4 addresses only (the original behavior). Proxies are
  resolved by the operating system.
- In default send-only mode, multiple requests may be in flight on one
  connection. On HTTP/2 the tool keeps up to 64 streams in flight per
  connection. In response-aware mode each thread has at most one request in
  flight; increase `THREADS` for more concurrency.
- Default send-only mode uses a 15-second write timeout when the server stops
  accepting data. Response-aware mode uses a 15-second per-request timeout.
- Default send-only mode counts successfully written requests. It cannot tell
  whether the server returned `2xx`, `4xx`, or `5xx`, and it does not measure
  latency. Use `--send-only=false` to check server health.
- Servers may close heavily pipelined connections; the tool reconnects with
  backoff automatically. On HTTP/2, a GOAWAY also triggers a reconnect.
- Send-only throughput is limited by client CPU, kernel/network bandwidth, and
  the target server. Start with a modest thread count and ramp up while watching
  both client and server resource usage.
- HTTP/1.1 send-only mode uses roughly 96 KiB of buffers per active connection
  (64 KiB batch + 32 KiB discard). HTTP/2 uses smaller per-frame buffers but
  keeps up to 64 stream slots. Very high `THREADS` values raise client memory
  use.
- TLS certificates are **not** verified, so self-signed home-lab certificates
  work. This is intentional and must not be used as a security check.
- `--xff` and `--cache-bust` intentionally make requests less browser-like. They
  are off by default and should only be used for proxy/CDN/cache testing.
- URL user:password credentials, proxy authentication, HTTP/3, and IPv6 direct
  targets are not supported. Proxy authentication is still unsupported even
  when rotating proxies.
- Fingerprint mimicry is a testing feature, not a guarantee of bypassing
  third-party bot protection. Only use it against servers you own or are
  explicitly authorized to test.

## Troubleshooting

- `Failed to load proxies.txt`: create `proxies.txt` in the current working
  directory (usually the folder you run the command from) and check the reported
  line number.
- `Initial DNS lookup failed`: the URL host must resolve to an IPv4 address from
  the machine running the tool.
- Many `timeouts` / `errors`: the server, network path, or proxy is saturated or
  unreachable. Check server logs and reduce threads.
- High `errors` in default send-only mode: some servers close pipelined or
  HTTP/1.0 connections after each response. The tool reconnects automatically;
  use `--send-only=false` to confirm the server's actual response status.
- TLS or HTTP/2 handshake errors: verify the target speaks TLS on the URL port.
  Use `--http2=false` to isolate an HTTP/2 negotiation problem and
  `--fingerprint=none` to compare against Go's standard TLS stack.
- `too many open files` (Linux/macOS): raise the shell's file-descriptor limit
  or use fewer threads.
- `--jitter`, `--cache-bust`, `--xff`, `--fingerprint`, `--http2`,
  `--proxy-rotation`, `--rotate-every`, or `--send-only=false` seems ignored:
  place flags before the URL; Go's flag parser stops at the first positional
  argument.
